# Regenerate the WinRT bindings

Most of `winui3/src/` (`src/Microsoft/`, `src/Windows/`) plus the feature
table in `winui3/Cargo.toml` are generated by the workspace's `bindgen` tool
from `.winmd` metadata files. Regeneration is triggered by adding a new
WinAppSDK version (the common case — full flow below) or changing the
filters in `bindgen/etc/winui3.txt`.

Background when needed: `bindgen/ARCHITECTURE.md` (inputs, generation passes,
post-process steps), `winui3/ARCHITECTURE.md` → "Adding a new WinAppSDK
version" (bootstrap details). This skill is the workflow; those are the
rationale.

Two facts that shape everything below:

- Bindings are generated from **one** SDK version — the newest supported.
  Older `WindowsAppSDKVersion` variants remain only as bootstrap targets, so
  "add support for 2.1" means "regenerate the whole surface from 2.1
  metadata, then add a 2.1 bootstrap variant".
- Each WinAppSDK bump so far has been additive. If the diff shows **removed
  public API**, stop and tell the user — that's the unresolved breaking-change
  scenario described in `bindgen/ARCHITECTURE.md` → "Known gap", and it needs
  a human decision, not a workaround.

## Step 1: Stage the winmds

```powershell
./bindgen/fetch-winmd.ps1 -Version 2.1        # WinAppSDK major.minor
./bindgen/fetch-winmd.ps1 -Version 2.1 -SkipRuntime   # plain regen, no new bootstrap variant
```

The script resolves the earliest stable patch of that minor via the
`Microsoft.WindowsAppSDK` meta-package nuspec (the split packages don't
version in lockstep with the SDK, so this is the only reliable resolution),
downloads the four source packages (cached in `$env:TEMP\winui3-winmd-cache`),
and stages the expected winmds flat into `bindgen/winmd/`. Pass an exact
meta-package version (e.g. `-Version 2.1.3`) to pin a specific servicing
release instead.

Unless `-SkipRuntime` is given it also prints a **"Bootstrap constants"**
block (runtime version u64 + package family name) — save it for step 3.

If the script errors with "not found in any package", a winmd listed in
`bindgen/etc/winui3.txt` moved or was renamed upstream; inspect the extracted
nupkgs in the cache dir and update the `--in` list (and the "Source packages"
table in `bindgen/ARCHITECTURE.md`) to match.

## Step 2: Regenerate

```bash
cargo run -p bindgen    # must be run from the workspace root (paths are cwd-relative)
```

This rewrites `winui3/src/Microsoft/**`, `winui3/src/Windows/**`, and the
feature table in `winui3/Cargo.toml`, then applies two post-process patches.
Both panic loudly rather than silently no-op:

- `patch_winui3_features` panics "feature X not emitted" → a `FEATURE_PATCHES`
  entry in `bindgen/src/main.rs` names a feature the generator no longer
  produces. Find out whether the namespace was renamed or dropped before
  touching the table.
- `promote_factory` panics "needle not found" → `windows-bindgen` changed its
  output format (typically after a version bump). Adjust the needle in
  `bindgen/src/main.rs`; the goal is only to make `IApplicationFactory` /
  `IPageFactory` `pub(crate)` for `xaml_app.rs` / `xaml_page.rs`.

## Step 3: Bootstrap variant (only when adding a new WinAppSDK version)

In `winui3/src/bootstrap/mod.rs`, using the values the script printed:

1. Add the two constants, following the existing naming pattern
   (`WINDOWSAPPSDK_RUNTIME_VERSION_UINT64_V2_1`, `..._PACKAGEFAMILYNAME_V2_1`).
2. Extend the `WindowsAppSDKVersion` enum and both `const fn` accessors.
3. Move the default in `PackageDependency::initialize()` to the new version —
   that is the standing policy for version bumps — unless the user explicitly
   asked to keep the old default. Call the change out in your summary, since
   apps pick up the new default silently.
4. Update the docs that enumerate supported versions — at minimum the
   `src/bootstrap/` bullet in `AGENTS.md`. Grep the `*.md` files for the
   previous version string (e.g. `V2_0`) to catch stragglers.

## Step 4: Validate

Run these in order — each catches what the previous can't:

1. `cargo check -p winui3 --all-features` — fast smoke test; catches
   references to `windows` crate items that no feature pulls in at all.
2. `./bindgen/check-features.ps1` — checks every feature **in isolation**
   (`cargo check -p winui3 --features <F>`, one feature at a time). This is
   the check that actually proves the feature table: under `--all-features` a
   sibling feature can mask another feature's missing dependency, so a
   feature can be broken for consumers while the union compiles fine. The
   first sweep is slow (each feature set builds its own `windows` variant);
   later sweeps reuse the cache.
3. `cargo build -p mica`, `cargo build -p simple-xaml-app`,
   `cargo build -p page-navigation` — **one `cargo build` invocation per
   sample, never `--workspace` or multiple `-p` flags.** Cargo unifies
   features across a single invocation, which turns on `XamlApp_Navigation`
   for samples that don't implement `TryResolveXamlType` and breaks their
   build spuriously.
4. `cargo fmt -p <crate>` for crates whose *hand-written* files you touched
   (`winui3` for bootstrap edits, `bindgen` for `main.rs` edits). The
   generated `Microsoft`/`Windows` trees are excluded from rustfmt
   (`#[rustfmt::skip]` on their module declarations in `lib.rs`) — never try
   to reformat them.

### The FEATURE_PATCHES loop

Symptom: step 4.1 or 4.2 fails with `E0433`/`E0412` ("cannot find X in Y",
often with a "found an item that was configured out" note) in a file under
`winui3/src/Microsoft/…`.

The failing module maps 1:1 to a cargo feature: strip `winui3/src/Microsoft/`
and join with `_` (`UI/Input/Interop/mod.rs` → `UI_Input_Interop`). The
unresolved path tells you the missing dependency: a `windows::…` path needs
the matching `windows/*` feature (`windows::Devices::Input` →
`windows/Devices_Input`); a `crate::…` path needs another `winui3` feature.

Fix it in `FEATURE_PATCHES` in `bindgen/src/main.rs` — extend the feature's
entry, or add a new row (keep the table sorted and column-aligned; it's
`#[rustfmt::skip]`). Then **re-run `cargo run -p bindgen`** and check again.
Never edit the feature table in `winui3/Cargo.toml` directly: the next
regeneration overwrites it, so a hand-edit is a fix that silently evaporates.

A new SDK often introduces new namespaces → new features. Those only need a
`FEATURE_PATCHES` row if step 4.1 or 4.2 says so — don't add speculative
entries.

Not every isolation failure is a `FEATURE_PATCHES` fix: if the unresolved
path is in *hand-written* code (`lib.rs`, `xaml_*.rs`), the right fix is
usually that item's `#[cfg(feature = …)]` gate — especially when the missing
feature dep would create a feature cycle (e.g. `xaml_typename` is gated on
`UI_Xaml`, not `UI_Xaml_Interop`, because `UI_Xaml` → `UI_Xaml_Interop`
already exists).

### Reviewing the diff

The generated diff is large; review it by shape, not line by line:

- `git diff --stat` first: churn should concentrate in the namespaces the
  release actually changed. A rewrite of *everything* usually means a
  `windows-bindgen` bump changed output style, not an API change.
- `git diff winui3/Cargo.toml` — the feature-table diff is the readable
  summary of what appeared. New features = new namespaces; check each
  compiles (step 4.1 covers this).
- Search the full diff for removals of `pub` items (`git diff | grep '^-.*pub '`)
  — additions are expected, removals are the breaking-change red flag from
  the top of this skill.
