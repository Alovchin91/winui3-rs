# winui3 architecture

This document covers the hand-written parts of the `winui3` crate and the
reasoning behind them. Most of the crate (`src/Microsoft/`, `src/Windows/`)
is WinRT bindings generated by `cargo run -p bindgen`; this doc is about
the small layer under `src/` that plugs gaps the generated bindings can't
fill.

Read this before rewriting, deduplicating, or removing any of the components
below. Every one exists for a reason that isn't obvious from the code alone.

## What the hand-written layer is for

Three gaps the generated bindings don't close:

1. **Pre-flight.** Things that must happen *before* any binding works — mainly
   locating and activating the Windows App SDK framework package for
   unpackaged apps.
2. **Off-the-grid APIs.** Windows entry points that aren't declared in any
   public WinMD (HWND ↔ `WindowId`, `IWindowNative`).
3. **Composition.** Letting Rust code extend composable WinRT runtime classes
   (`Application`, `Page`). `windows-core`'s `#[implement]` macro doesn't yet
   emit the composition dance.

Plus a bit of glue: boxed value types (`Reference<T>`), custom XAML metadata
(`XamlCustomType`), apartment init.

## Non-goals: XAML markup files

This crate lets Rust apps drive WinUI 3 **from code**. It does not, and will
not, support loading UI from `.xaml` markup files. Apps build their UI
imperatively (see `samples/page-navigation/src/sample_page.rs` for the shape
— `OnNavigatedTo` constructs the tree).

Reaching markup parity would mean owning a XAML compiler producing XBF
output, generating `XamlTypeInfo.g.*`-equivalent metadata, an `IXamlMember`
infrastructure for markup-set properties, codegen for `InitializeComponent`
field population, xmlns registration, and a full `IXamlType` chain with a
real `BaseType` lookup. The complexity isn't justified by what this crate is
trying to be.

Concretely:

- Stub-quality methods on `XamlCustomType` (`GetMember`, `ContentProperty`,
  `IsBindable`, etc. returning empty/false; `RunInitializer` as a no-op) are
  intentional. They're never queried by the code-driven flows the crate
  supports.
- `XamlAppOverrides::TryResolveXamlType` exists for `Frame::Navigate`'s
  custom-type lookup, not as a hook for markup-side type resolution.
- `XamlControlsXamlMetaDataProvider` is composed in for built-in type
  lookups; the crate never reaches for the equivalent user-side provider
  because there's no markup pipeline to feed it.

Don't propose work that exists only to make markup loading possible.
Improvements that strengthen the code-driven surface (a delegating
`XamlSystemBaseType`, a real `RunInitializer` hook for Rust-defined
DependencyProperties, etc.) are still on the table.

## `src/bootstrap/` and the `MsixDynamicDependency` feature

`PackageDependency::initialize[_version]()` pins a dependency on the Windows
App SDK framework package (e.g. `Microsoft.WindowsAppRuntime.2_8wekyb3d8bbwe`
— note 2.0+ aligns the PFN with the major version only, while 1.x used
`Microsoft.WindowsAppRuntime.1.8_8wekyb3d8bbwe` and similar), splices it into
the process' package graph via `AddPackageDependency`, and captures the
package's full name + install path. `Drop` undoes both operations.

This bootstrap is required for **unpackaged** apps. WinUI 3 lives in a
framework MSIX package that isn't in an unpackaged process' package graph by
default; without the bootstrap, WinRT activation of `Microsoft.UI.*` types
fails.

### Adding a new WinAppSDK version

The `WINDOWSAPPSDK_RUNTIME_VERSION_UINT64_V*` and
`WINDOWSAPPSDK_RUNTIME_PACKAGE_FRAMEWORK_PACKAGEFAMILYNAME_V*` constants in
`src/bootstrap/mod.rs` come from the `WindowsAppSDK-VersionInfo.json` file
bundled inside the `Microsoft.WindowsAppSDK.Runtime` NuGet package (starting
with v1.8). The fields we need:

- `Runtime.Version.HexUInt16` → the `u64` version constant
- `Runtime.Packages.Framework.PackageFamilyName` → the package family name

To add support for a new major.minor release:

1. Run `./bindgen/fetch-winmd.ps1 -Version <major.minor>` — it resolves the
   matching `Microsoft.WindowsAppSDK.Runtime` release, extracts
   `WindowsAppSDK-VersionInfo.json`, and prints both values. (Manual
   fallback: download the Runtime `.nupkg` from NuGet, extract it — it's a
   zip — and read the JSON fields above.)
2. Add two new constants in `src/bootstrap/mod.rs` using those values.
3. Extend the `WindowsAppSDKVersion` enum and its two `const fn` accessors.
4. Bump the default used by `PackageDependency::initialize` unless there's
   an explicit reason not to.

### Why `dynamic_dependency.rs` exists

~300 lines of hand-written FFI that mirror
`windows::Win32::Storage::Packaging::Appx`. Selected by the
`MsixDynamicDependency` cargo feature.

This is **load-bearing for Windows 10 support**:

- WinAppSDK supports Windows 10 v1809 (build 17763) and up.
- The OS-level MSIX dynamic-dependency APIs in
  `windows::Win32::Storage::Packaging::Appx`
  (`TryCreatePackageDependency`, `AddPackageDependency`, etc.) only exist on
  Windows 11 (build 22000) and newer.
- With the feature on, the code links against
  `Microsoft.WindowsAppRuntime.dll` (shipped alongside the .exe, bundled with
  WinAppSDK) — works on Windows 10 v1809+.
- With the feature off, it resolves against OS-level symbols — Windows 11 only.

**The two code paths are not redundant duplication.** They are the switch
between "runs on Windows 10" and "Windows 11 only". Any app that wants to run
on Windows 10 needs the feature on.

## `src/interop.rs`

Runtime-loads `Microsoft.Internal.FrameworkUdk.dll` and looks up
`Windowing_GetWindowIdFromWindow` / `Windowing_GetWindowFromWindowId` — used
to convert between Win32 `HWND` and WinUI 3's `Microsoft::UI::WindowId`. Also
hand-declares the `IWindowNative` COM interface
(`eecdbf0e-bae9-4cb6-a68e-9598e1cb57bb`), which exposes a XAML `Window`'s
underlying `HWND`.

Neither the C functions nor `IWindowNative` are declared in any public WinMD.
Apps that mix Win32 and XAML need the HWND bridge — see the `mica` sample's
use of `GetWindowFromWindowId` to pass an HWND to `ICompositorDesktopInterop`.

Loaded function pointers are cached in a `std::sync::OnceLock<InteropImpl>`.

## `src/reference.rs`

`Reference<T>`: a generic `IReference<T>` implementation used wherever a
WinRT API wants a boxed value type that `windows::Foundation::PropertyValue`
can't produce. Example: `AppWindowTitleBar::SetButtonBackgroundColor` takes
`IReference<windows::UI::Color>`, and `PropertyValue` doesn't support
`Color`. See the `mica` sample:

```rust
title_bar.SetButtonBackgroundColor(Reference::new(Colors::Transparent()?))?;
```

`PropertyValue` is a factory with a fixed set of supported types (UInt32,
Boolean, String, etc.). `Reference<T>` is the escape hatch for everything
else.

`IReference<T>` inherits `IPropertyValue`, so implementors must provide both
vtables. In `Reference<T>`, every `IPropertyValue` getter (`GetUInt8`,
`GetString`, etc.) returns `E_NOTIMPL` **intentionally**:

- For types `PropertyValue` *can* handle, callers should use `PropertyValue` —
  not `Reference<T>`.
- `Reference<T>` is the complement, not the general case.

**Don't** propose filling in the `IPropertyValue` getters, even when `T`
matches a primitive — that would encourage misuse.

## `src/xaml_app.rs` and `src/xaml_page.rs`

Each file contains ~300 lines of manually-expanded `#[implement]` macro
output: vtables, `QueryInterface`, refcount, and the composition dance that
obtains an inner `IInspectable` via `IApplicationFactory::CreateInstance` /
`IPageFactory::CreateInstance`.

`Application` and `Page` are **composable (unsealed)** WinRT runtime classes —
they're designed to be extended this way. The `#[implement]` macro in
`windows-core` doesn't yet emit the composition dance, so we do it by hand.

### Why `Application` specifically needs factory composition

The app's bootstrap code (creating the main window, wiring resources) has to
live in `IApplicationOverrides::OnLaunched`. In principle we could implement
only `IApplicationOverrides` and attach it to an `Application` some other
way, but `IApplicationFactory::CreateInstance` is what registers the composed
instance as the singleton returned by `Application::Current()`. Going through
the factory is the only way to make the composed outer object be that
singleton.

The instance produced by `XamlApp::compose` (see the `simple-xaml-app`
sample) is not held anywhere by user code — its lifecycle is bounded entirely
by `Application::Start()`.

### Why `Page` uses the same shape

`Page` is the unit of navigation inside
`Microsoft::UI::Xaml::Controls::Frame`. `IPageOverrides` provides
`OnNavigatedTo` / `OnNavigatedFrom` / `OnNavigatingFrom`. The
factory-composition pattern here may not be strictly required — there may be
a cleaner alternative — but today it mirrors the `Application` approach.

### Tracking upstream

[windows-rs#3767 — "Consider implementing limited support for COM aggregation"](https://github.com/microsoft/windows-rs/issues/3767).
Filed against `winui3-rs`. Not a priority for the `windows-rs` maintainers.

**Don't** refactor / deduplicate / reshape the hand-expanded code in
`xaml_app.rs` or `xaml_page.rs`. Revisit when `windows-rs#3767` is resolved —
at that point, both files should collapse to small users of the new macro.

### Why `cargo run -p bindgen` patches factory visibility

`xaml_app.rs` calls `Application::IApplicationFactory(...)`; `xaml_page.rs`
calls `Page::IPageFactory(...)`. The generated bindings mark those functions
private by default. The bindgen tool's `promote_factory` helper rewrites them
to `pub(crate)` after generation so the composition code can reach them. See
`bindgen/src/main.rs`.

## `src/xaml_types.rs`

`IXamlType` implementations used by `XamlApp`'s `GetXamlType` /
`GetXamlTypeByFullName` hooks.

- **`XamlSystemBaseType`** — represents a built-in XAML type. Used as the
  `BaseType` of a custom type.
- **`XamlCustomType<T: Activatable>`** — represents a user-defined type.
  `ActivateInstance` calls `T::activate()`.

### Why `XamlCustomType` is Page-only on purpose

Only one constructor is wired up — `XamlCustomType::for_page` — and it
hardcodes `Microsoft.UI.Xaml.Controls.Page` as the base.

The whole purpose of `XamlCustomType` is to build the `IXamlType` that
`Frame::Navigate()` needs. In .NET, `Frame::Navigate(typeof(MyPage))` works
because `System.Type` carries the type identity. There's no equivalent in
Rust, so `XamlCustomType::for_page` constructs an `IXamlType` that wraps a
user's Rust struct implementing `XamlPageOverrides`, with `Page` as its base.

Other composable XAML types (`ContentDialog`, `UserControl`, …) aren't in the
navigation flow and don't need an `IXamlType` construction helper. The
`<T: Activatable>` type parameter is there to parameterize over the specific
page struct, not as a hook for generalizing to other bases.

**Don't** propose generalizing to other bases (e.g. `for_content_dialog`)
just because the type parameter looks extensible. There's no current call
site that needs it. If a Rust-implemented custom control that XAML has to
instantiate by name ever appears, revisit then.

## `src/lib.rs`

Module declarations, cfg-gated re-exports, and three small helpers:

- `init_apartment(ApartmentType)` — thin wrapper around `RoInitialize`.
- `Activatable` trait — the seam between `XamlCustomType<T>` and user code.
- `xaml_typename(&str)` — constructs `TypeName { Name, Kind: Custom }` from a
  string.

## Putting the navigation pieces together

`XamlApp` alone is enough to run an app — the `simple-xaml-app` sample
never navigates. The components below are what you need *on top of*
`XamlApp` (gated behind the `XamlApp_Navigation` cargo feature) to make
`Microsoft::UI::Xaml::Controls::Frame::Navigate` resolve a
Rust-implemented page. `samples/page-navigation` is the canonical example;
the integration story:

1. **Define a page.** A user struct (e.g. `SamplePage`) implements
   `XamlPageOverrides` (the `On{Navigated,Navigating}{To,From}` callbacks)
   plus `Activatable`. Its `activate()` calls `XamlPage::compose(self)` and
   returns the result as an `IInspectable`.

2. **Teach the XAML metadata layer about it.** The same struct that
   implements `XamlAppOverrides::OnLaunched` also implements
   `TryResolveXamlType`. When XAML asks for a custom type by full name,
   match the page's canonical full name (e.g. `"SamplePage"`) and return
   `XamlCustomType::<SamplePage>::for_page(h!("SamplePage"))`. The string
   passed to `for_page` becomes the resulting `IXamlType`'s `FullName`,
   and that has to be the same name XAML asked for — the framework treats
   it as the type's identity downstream (navigation history,
   `Frame::SourcePageType`, back/forward stack comparisons).

3. **Navigate.** Build a `Frame`, then call
   `frame.Navigate2(&xaml_typename("SamplePage"))`. `Navigate2` takes a
   `TypeName { Kind: Custom }`, which routes through `TryResolveXamlType`
   from step 2, which produces an `IXamlType` whose `ActivateInstance`
   calls `SamplePage::activate()` from step 1.
