# AGENTS.md

This file provides guidance to coding agents when working with code in this repository.

**Scope:** code-driven WinUI 3 UI from Rust. XAML markup file support (`.xaml` files, `InitializeComponent`-style codegen, `IXamlMember` for markup-set properties) is explicitly a non-goal — see `winui3/ARCHITECTURE.md` → "Non-goals: XAML markup files" for what this means in practice.

## Workspace layout

Cargo workspace (resolver 2, Rust 1.82+, edition 2021):

- `winui3/` — the library crate. Default workspace member. Mostly generated WinRT bindings (`src/Microsoft/`, `src/Windows/`) plus a small layer of hand-written code.
- `bindgen/` — internal tool (`publish = false`) that regenerates the bindings. Not built by default.
- `samples/*` (`mica`, `page-navigation`, `simple-xaml-app`) — example apps that depend on `winui3` with specific feature sets.

## Common commands

```bash
# Build just the library (default member)
cargo build

# Build/run a sample (each sample selects its own winui3 features)
cargo run -p mica
cargo run -p simple-xaml-app

# Regenerate bindings (see "Regenerating bindings" below — needs winmd files staged first)
cargo run -p bindgen
```

After editing Rust sources, run `cargo fmt -p <crate>` for the crate(s) you touched (or `cargo fmt --all` for workspace-wide changes). Tabular/aligned data worth preserving (e.g. `FEATURE_PATCHES` in `bindgen/src/main.rs`) uses `#[rustfmt::skip]`.

**Don't validate via `cargo build --workspace` or `cargo build -p page-navigation -p simple-xaml-app`.** Workspace feature unification turns on `XamlApp_Navigation` for *all* sample compilations as soon as any one of them enables it; samples that don't implement `TryResolveXamlType` (`simple-xaml-app`) then fail to compile. Build each sample individually with its own `cargo build -p <sample>` invocation.

### Validation for ordinary edits

Run checks from the workspace root. Plain `cargo build` uses the empty default feature set, so it does not compile the optional helpers. Select checks for the area you changed; each command below is a separate invocation.

| Changed area | Compile checks |
| --- | --- |
| `src/bootstrap/` | `cargo check -p winui3 --no-default-features` and `cargo check -p winui3 --no-default-features --features MsixDynamicDependency` cover both dependency paths. |
| `src/interop.rs` | `cargo build -p mica` checks a consumer of the HWND bridge. |
| `src/reference.rs` | `cargo check -p winui3 --no-default-features --features Foundation` checks the minimal feature set; `cargo build -p mica` checks a consumer. |
| `src/xaml_app.rs` | `cargo build -p simple-xaml-app` and `cargo build -p page-navigation` cover application composition with navigation disabled and enabled. |
| `src/xaml_page.rs`, `src/xaml_types.rs` | `cargo build -p page-navigation` checks the navigation integration. |
| `src/lib.rs` feature gates | `cargo check -p winui3 --no-default-features`, plus `./bindgen/check-features.ps1 -Feature Foundation,XamlApp` with the feature list adjusted to the gates you changed. |

For regeneration or generated feature-table changes, use the skill's full validation sequence, including every feature in isolation. Compile checks do not establish runtime behavior; for UI or lifecycle changes, also run the affected sample and report what you exercised.

## Feature-flag model

`winui3` has a large generated feature table in `winui3/Cargo.toml`. Rules:

- Default feature set is empty. Consumers opt in to the WinRT namespaces they need (e.g. `UI_Xaml`, `UI_Composition_SystemBackdrops`, `UI_Dispatching`, `UI_Windowing`).
- Features map 1:1 to the `Microsoft.UI.*` / `Windows.*` namespace tree; they're additive and pull in matching `windows` crate features.
- Hand-written convenience features on top of the generated ones:
  - `Foundation` — enables `Reference<T>` (`src/reference.rs`).
  - `XamlApp` — enables `XamlApp` / `XamlAppOverrides` (subclassable `Application`).
  - `XamlApp_Navigation` — adds `XamlPage` / `XamlPageOverrides` / `XamlCustomType` and enables custom XAML type resolution on top of `XamlApp`.
  - `MsixDynamicDependency` — bootstrap uses the bundled `Microsoft.Windows.ApplicationModel.DynamicDependency` P/Invokes (`src/bootstrap/dynamic_dependency.rs`) instead of the `windows` crate's versions. Kept behind a flag because the Win32 Appx APIs for dynamic dependency were added later.

Samples' `Cargo.toml` files are the canonical examples of which features to turn on for which API.

## Hand-written layer (big picture)

Most of `winui3/src/` is autogenerated — these are the handwritten helpers that let a pure-Rust app actually use WinUI 3. **See `winui3/ARCHITECTURE.md` for the rationale behind each component; read it before modifying anything under `winui3/src/` that isn't generated.**

- `src/bootstrap/` — `PackageDependency::initialize[_version]()` activates the Windows App SDK framework package (`WindowsAppSDKVersion::V1_5..V1_8`, `V2_0..V2_1`; default `V2_1`). Must be called before any WinUI 3 API. The `MsixDynamicDependency` cargo feature is disabled by default, selecting OS-level dynamic-dependency APIs (Windows 11+ only). Enabling it selects bundled Windows 10-compatible MDD entry points — preserve both paths.
- `src/interop.rs` — HWND ↔ `Microsoft::UI::WindowId` conversion and `IWindowNative`, loaded from `Microsoft.Internal.FrameworkUdk.dll`. Not in any WinMD.
- `src/reference.rs` — `Reference<T>`: generic `IReference<T>` for types `windows::Foundation::PropertyValue` can't box (e.g. `IReference<Color>`). `IPropertyValue` methods intentionally return `E_NOTIMPL` — for primitive types use `PropertyValue`.
- `src/xaml_app.rs`, `src/xaml_page.rs` — hand-expanded `#[implement]` machinery for composing with the unsealed runtime classes `Application` and `Page`. Calls the bindgen-patched-to-`pub(crate)` factories `IApplicationFactory` / `IPageFactory`. Blocked on [windows-rs#3767](https://github.com/microsoft/windows-rs/issues/3767) — **don't refactor, deduplicate, or reshape the hand-expanded composition machinery.**
- `src/xaml_types.rs` — the `XamlCustomType` metadata needed for `Frame::Navigate`. Improvements to the code-driven surface, including the items in `winui3/TODO.md`, are allowed; preserve the Page-only scope and the XAML markup non-goal.
- `lib.rs` — `init_apartment()`, the `Activatable` trait, `xaml_typename()`.

Top-level module convention: `crate::Microsoft::...` mirrors the `Microsoft.*` WinMD namespaces; `crate::Windows::...` re-exports a small pinned subset (currently just `Windows.UI.Xaml.Interop`) that must be generated alongside WinUI because of a known `windows-bindgen` bug — see below.

## Regenerating bindings

**Always work through the `regenerate-bindings` skill** for any regeneration or WinAppSDK version work — it packages the full workflow (winmd staging via `bindgen/fetch-winmd.ps1` → `cargo run -p bindgen` → bootstrap variant → feature-isolation validation) with the failure modes and fix loops spelled out. Invoke it before improvising from the notes below. (Plain version bumps of the `windows` / `windows-bindgen` dependencies are manual work, not a trigger for the skill.)

`cargo run -p bindgen` is the entry point. Must be invoked from the workspace root, and `bindgen/winmd/` must be populated with the expected `.winmd` files first (gitignored — sourced from specific NuGet packages).

**See `bindgen/ARCHITECTURE.md`** for the full procedure: which NuGet packages to pull, how to pick versions, what the two generation passes and two post-process steps do, and known gaps. Open backlogs: `winui3/TODO.md`, `bindgen/TODO.md`.

Adding a new `WindowsAppSDKVersion` variant to the bootstrap module is a separate, additional step — the runtime version `u64` and package family name come from `WindowsAppSDK-VersionInfo.json` in the `Microsoft.WindowsAppSDK.Runtime` NuGet package (not one of the four bindgen packages). See `winui3/ARCHITECTURE.md` → "Adding a new WinAppSDK version".

## Runtime requirement

WinUI 3 apps built with this crate need the Windows App SDK runtime (framework package) installed on the target machine. `PackageDependency::initialize()` is what acquires it at startup; without that call, WinRT activation of `Microsoft.UI.*` types will fail. The sample binaries are unpackaged — they rely on the dynamic-dependency bootstrap, not on an MSIX manifest.
